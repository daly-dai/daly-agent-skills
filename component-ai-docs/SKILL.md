# Component AI Docs

> 盘活项目中的业务组件——让 AI 认识你项目里那些没有文档的存量组件。

**核心问题**: AI 写前端代码时，不知道项目里有哪些业务组件、接受什么 Props、什么时候该用什么时候不该用。

**解决思路**: 通过深度搜集组件源码、关联类型、真实使用案例，生成 AI 可消费的标准文档。高频组件优先，分批推进。

---

## 核心原则

1. **开发者最了解组件。** `metadata.json` 里的"何时用/何时不用"只有人能写对——Skill 的角色是引导写出来，不是替代判断。
2. **JSDoc 写给人看的不等于写给 AI 看的。** "用户名称"是给人看的，"必填，用于表格列渲染和搜索条件"是给 AI 看的。
3. **先盘核心，再补全量。** 20 个组件里高频使用的可能就 5 个，优先盘活这几个。
4. **真实案例胜过编造示例。** 项目里已有大量使用案例，搜集它们比 AI 编造示例更有价值。

---

## 输出格式标准

> 这是本 Skill 的"输出锁"——最终产出的文档必须符合以下格式。

### 目录结构

```
.ai/project-components/
├── README.md                    # 索引层：组件速查表（用途 + 边界 + 一句话描述）
└── components/
    ├── UserTable.md             # 详情层：完整 Props + 使用案例
    ├── StatusBadge.md
    └── ...
```

### README.md 索引层（给 AI 第一步看）

AI 先读这个，快速判断"有没有我能用的组件"，再按需读取具体组件的详情文件。不一次性全读。

### components/{Name}.md 详情层（给 AI 要用时看）

每个文件应包含：

1. **使用边界**（最优先）：何时适用、何时不适用、优先替代
2. **子组件/静态方法**：如 `SForm.useWatch`、`SButton.Group`
3. **类型定义**：Props 接口 + 关联类型，含 JSDoc 描述
4. **组合组件引用**：本组件 Props 里引用了哪些外部类型，内联它们的核心属性
5. **实际使用示例**（从项目真实代码中提取）：2-3 个覆盖不同场景的使用案例，附简要说明

### metadata.json 字段标准

由 Skill 辅助生成，人工确认：

```json
{
  "useWhen": [
    "管理后台标准列表页（搜索 + 表格 + 分页）"
  ],
  "dontUseWhen": [
    "纯展示表格，无搜索条件，直接用 STable"
  ],
  "prefer": {
    "STable + SForm.Search + useSearchTable": "需要更精细控制时"
  }
}
```

| 字段 | 意义 | 写作要求 |
|------|------|---------|
| `useWhen` | 这个组件**应该**用的场景 | 用业务语言描述，不要写技术实现。好："需要搜索+表格+分页联动的列表页"。差："当需要 SSearchTable 时"。 |
| `dontUseWhen` | 看起来像但**不应该**用这个组件的场景 | 每条必须给出替代方案（"直接用 XXX"）。这是 AI 最需要的信息。 |
| `prefer` | 在这个场景下**优先用别的** | key=更优方案，value=什么时候用那个方案 |

## 执行流程

### 步骤 1：组件清单扫描 + 复杂度评估

扫描目标目录（默认 `src/components/`），列出所有组件，并搜索项目中的引用计数：

```
组件名          目录              类型文件      子组件  引用数  复杂度   优先级
──────────────────────────────────────────────────────────────────────────
UserTable       src/components/   types.ts ✅   有 Modal  12处   🔴 高   🔴 高（列表页核心）
StatusBadge     src/components/   types.ts ✅   无         8处   🟡 中   🟡 中
DataChart       src/components/   内联类型       无         3处   🟡 中   🟡 中
OldReport       src/components/   无类型文件     无         0处   🟢 低   🟢 低（疑似废弃）
```

**引用计数**：在 `src/` 目录下搜索 `import ... from '...<ComponentName>'` 的出现次数。

**复杂度评估**（影响分批策略）：
- 🔴 高复杂度：Props > 15 个、有子组件/静态方法、内部状态复杂、被广泛引用（> 8 处）
- 🟡 中复杂度：Props 5-15 个、无子组件、引用 3-8 处
- 🟢 低复杂度：Props < 5 个、纯展示类、引用 < 3 处

优先级判断依据：
- 🔴 高：被多个页面引用、位于路由页面中、名字含 Table/Form/Detail
- 🟡 中：被引用但范围有限、纯展示类
- 🟢 低：无引用、名字含 Old/Deprecated、文件最近未修改

**分批建议**：根据复杂度自动编排批次：
- 高复杂度组件：单独一批（确保充分搜集）
- 中复杂度组件：每批 2-3 个
- 低复杂度组件：每批 3-5 个

向用户确认优先级、分批方案和范围："共发现 N 个组件，其中 X 个高优先级。按复杂度分为 Y 个批次，建议从高优先级开始逐批推进。"

### 步骤 2：深度信息搜集（按批次进行）

> **分批策略**：由于弱模型上下文有限（128K），不要一次性处理所有高频组件。
> - **复杂组件**（Props 多、有子组件、被广泛引用）：**单独一批**，确保搜集充分
> - **中等组件**：每批 2-3 个
> - **简单组件**（Props 少、纯展示类）：每批 3-5 个
>
> 每批处理完后向用户确认，再开始下一批。批次之间的上下文可以释放。

对当前批次中每个组件，执行以下搜集流程：

**2a. 组件源码读取（基础层）**

1. 读取源码（`.tsx` 或 `.tsx` + `types.ts`）
2. 提取 Props 信息：
   - 如果 `types.ts` 中有独立 interface → 直接提取所有属性 + JSDoc
   - 如果类型内联在 `.tsx` 中 → 解析 function 参数或 React.FC<>
   - 如果使用了 PropTypes → 从 PropTypes 推导类型
   - 如果完全没有类型 → 从代码中使用方式推导参数名和用途，标注 `[?]`
3. 提取子组件（如 Modal、Drawer、内部注册的静态方法）

**2b. 关联类型搜集（类型层）**

在项目中搜索与组件相关的类型定义，扩大搜索范围：

1. **`src/types/` 目录**：搜索与组件名、Props 中引用的类型名相关的 interface/type
2. **`src/api/` 目录**：搜索调用该组件时对应的请求/响应类型（如 `requestFn` 的入参出参类型）
3. **组件内部 import**：追踪组件自身导入的外部类型，找到定义位置并提取

搜索方法：
- 按组件名搜索（如 `UserTable` → 搜 `UserTable`、`User` 相关类型）
- 按 Props 中引用的类型名搜索（如 Props 里有 `columns: ColumnType[]` → 找到 `ColumnType` 的定义）
- 按 API 路径搜索（如组件关联的接口 `/api/user/list` → 找对应的请求/响应类型）

**2c. 实际使用案例搜集（案例层）**

在项目中搜索该组件的所有实际调用位置：

1. **`src/pages/` 或 `src/views/`**：搜索 `import { ComponentName }` 或 `<ComponentName` 的使用位置
2. **`src/hooks/`**：搜索与组件配合使用的自定义 hooks
3. **测试文件**（`__tests__/`、`*.test.*`、`*.spec.*`）：搜索组件的测试用例

搜集要点：
- 每个组件至少找到 **2-3 个不同场景的使用案例**（不同页面、不同传参方式）
- 记录每个案例的**文件路径 + 关键代码片段**（不需要全部代码，只要组件调用部分）
- 特别关注：
  - 传了哪些 Props、用什么值
  - 与哪些其他组件组合使用
  - 是否有特殊的回调处理逻辑（如 `onSubmit`、`onChange`）
  - 是否有条件渲染或动态 Props

如果某个组件的使用位置超过 10 处，选取**最具代表性的 3-5 处**（覆盖不同场景即可）。

**2d. 信息汇总**

将 2a-2c 搜集的信息汇总，形成该组件的完整信息画像：
- 组件本身的 Props 类型 + JSDoc
- 关联的外部类型定义（从 src/types/、src/api/ 等处搜集到的）
- 2-3 个精选的实际使用示例（从真实代码中提取，非 AI 编造）

### 步骤 3：推导使用边界，生成 metadata.json 草稿

读取组件代码逻辑和引用位置，推导 `useWhen` / `dontUseWhen` / `prefer`：

- **useWhen**：从组件名 + 渲染内容 + 实际使用场景推导。"UserTable" → "用户数据列表展示"
- **dontUseWhen**：从代码中寻找 if/switch/return null 等边界逻辑推导，结合实际案例中**没有出现**的用法
- **prefer**：检查组件内部是否引用了更基础的组件（如用了 STable 自己又包了一层 → prefer STable）

所有推导项标 `[? 待确认]`。

### 步骤 4：人工确认环节

对每个组件，输出一份简短的确认清单：

```
=== StatusBadge (🟡 中优先级) ===

类型提取：
  ✅ Props: { status: string, size?: 'small'|'default' }
  ✅ 有 JSDoc
  [?] metadata.useWhen: "需要将状态码映射为彩色标签时" — 准确吗？
  [?] metadata.dontUseWhen: 不确定 — 状态为 null 时这个组件会显示什么？

实际使用示例（搜集到 N 处调用）：
  ✅ 示例 1：src/pages/order/list.tsx — 订单状态展示（status + size='small'）
  ✅ 示例 2：src/pages/user/detail.tsx — 用户状态展示（status + 自定义 color）
  [?] 示例 3：src/pages/dashboard/index.tsx — 看起来是废弃用法，是否跳过？

请逐条确认或补充。
```

### 步骤 5：生成 .ai/ 文档

确认完成后，按标准格式生成：
- `.ai/project-components/README.md` — 索引
- `.ai/project-components/components/{Name}.md` — 详情

每个 `{Name}.md` 的结构：

```markdown
# ComponentName

## 使用边界
- **何时用**：...
- **何时不用**：...（替代方案：...）

## 子组件/静态方法
- `ComponentName.Sub`：...

## 类型定义
（Props 接口 + 关联类型的完整定义，含 JSDoc）

## 组合组件引用
（本组件 Props 里引用的外部类型，内联核心属性）

## 实际使用示例

> 以下示例均从项目真实代码中提取，非 AI 编造。

### 示例 1：{场景描述}
> 来源：`src/pages/xxx/xxx.tsx`

（精简后的代码片段，保留组件调用部分，省略无关逻辑）

**要点**：说明这个示例展示了什么用法、传了哪些关键 Props

### 示例 2：{场景描述}
> 来源：`src/pages/yyy/yyy.tsx`

...
```

**使用示例的写作规范**：
- 示例代码从真实项目代码中提取，**不是 AI 编造的**
- 每个示例保留组件调用的核心部分，去掉无关的业务逻辑和 import
- 每个示例附带**来源文件路径**，方便追溯
- 每个示例用 1-2 句话说明展示了什么场景/用法
- 不同示例应覆盖不同的使用场景（如：基础用法、带回调、组合使用、条件渲染等）

### 步骤 6：进入下一批次

当前批次处理完成后：
1. 向用户汇报本批次成果（生成了几个组件的文档）
2. 确认用户是否继续处理下一批次
3. 如果继续，从步骤 1 的清单中取出下一批组件，重复步骤 2-5
4. 所有批次处理完成后，更新 `README.md` 索引，确保覆盖所有已处理组件

## JSDoc 写法规范（给 AI 看的）

> 目标：让 AI 看到 JSDoc 就知道字段怎么用。

### Props 顶层 JSDoc

```
/**
 * SSearchTable 搜索表格组件 Props
 *
 * 集成 SForm.Search + STable 的一体化组件，是管理后台列表页的首选方案。
 * 自动处理搜索、分页、数据加载的联动逻辑。
 *
 * @example
 * <SSearchTable
 *   requestFn={async (params) => ({ dataList, totalSize })}
 *   formProps={{ items: [...], columns: 3 }}
 *   tableProps={{ columns: [...], rowKey: 'id' }}
 * />
 */
```

要点：一句话定位 + 核心能力 + 最小可运行示例。

### 属性级 JSDoc

```
好：
  /** 数据请求函数。接收搜索参数+分页参数，返回 { dataList, totalSize } */
  requestFn: (data?: any) => Promise<any>;

  /** 搜索表单列数，默认 3 */
  columns?: number;

  /** 表格区域标题。不传则无标题栏 */
  tableTitle?: STitleProps;

差：
  /** 请求函数 */
  requestFn: Function;

  /** columns */
  columns?: number;
```

规则：
- 说清楚"什么时候需要设这个字段"和"不设会怎样"
- 引用其他类型时说明"来自哪个组件/接口"
- 默认值必须写明
- 必填字段可以简短，但必须说清楚用途
